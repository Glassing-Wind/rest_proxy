Question: Trace the major ranking and fallback stages used by code search.

The MCP `search_codebase` pipeline is **hybrid retrieval → heuristic ranking → targeted rescue → deduplication → coverage limits → optional grep supplement**. Its final ordering is substantially more than the initial vector/full-text score.

1. **Entry and query interpretation.** The tool embeds the query, then calls `search_codebase_core`; an empty embedding produces an error immediately. The core extracts implementation intent, query class, identifiers, member expressions, and path hints. Classification distinguishes usages, API definitions, explanations, and symbol searches using textual heuristics. [semantic.py:190](/Users/michaelmarler/Projects/rest_proxy/tools/brain/search/semantic.py:190), [code_retrieval.py:93](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:93), [retrieval_intent_queries.py:97](/Users/michaelmarler/Projects/rest_proxy/memory/retrieval_intent_queries.py:97)

2. **Initial PostgreSQL ranking.** Each project fetches up to `min(k * 10, 150)` candidates. Semantic ranking uses pgvector cosine distance; keyword ranking uses PostgreSQL `ts_rank` with `websearch_to_tsquery`. Fusion is:
   `2 / (60 + semantic_rank) + 1 / (60 + keyword_rank)`.
   **The join starts from semantic candidates**, so keyword-only matches cannot independently enter this initial result set. Projects are searched concurrently and their candidates combined. 3. **Filtering and heuristic reranking.** Defaults exclude test paths. Metadata, language, path, and Cargo-crate filters narrow candidates; optional Cargo graph enrichment fails open. Ordinary queries receive metadata boosts and penalties for documentation, parser data, and binding surfaces. Implementation queries receive richer bonuses and penalties for symbols, definitions, roles, entrypoints, dispatchers, routing, and other signals. Crucially, sorting uses a **lexicographic priority tuple**: surface penalties and structural priorities precede `rank_score`, so a higher fused score does not guarantee a higher final rank. Implementation searches also prefer available code candidates over parser data, binding surfaces, and documentation. 4. **Targeted candidate rescues.** These are distinct from the public `fallback="grep"` setting:
   - Empty initial retrieval can recover indexed rows from runtime-entrypoint paths or path hints; otherwise it returns empty.
   - With implementation intent and path hints, the top five results are checked for missing path/entrypoint matches. Additional indexed rows are loaded and reranked. Definition-preferring queries can then grep for definitions and load matching files’ indexed chunks.
   - Usage queries lacking a top-five exact member usage site can grep for member usages, load indexed chunks, and prioritize exact usage matches.

   These rescues supplement retrieval; they still depend on indexed chunks for ranked content. Path restrictions are reapplied afterward. 5. **Duplicate handling and final selection.** Optional Neo4j clone-group deduplication runs first and catches failures. With file deduplication enabled, a conditional duplicate-aware reranker delegates to `ts_pack`; missing capabilities can fall back through runtime calls, duplicate analysis, or retaining candidates. Implementation ordering is reapplied, then one chunk per file is selected. Finally, per-file and directory caps run before taking the first `k` results. 6. **Final grep supplement.** When enabled, it runs only if results exist and either there is at most one unique file or `unique_files / results <= fallback_ratio` (default `0.4`). It searches query-derived token alternatives using `rg -l` and appends file paths separately; it does not fuse them into ranked chunks. Thus this stage does **not** recover an empty result set. Broad mode enables grep by default, raises the default directory cap, and removes the default metadata boost. **Separate backend fallback:** `memory/store_search.py::search_codebase` implements another path: equal-weight vector/keyword RRF, vector-only search when query text is absent, and Neo4j vector fallback when PostgreSQL is unavailable or raises. Successful PostgreSQL searches returning zero rows do not trigger that fallback. Graph context is appended afterward. The MCP tool above calls the core directly, so this separate Neo4j fallback does not protect its PostgreSQL retrieval.
