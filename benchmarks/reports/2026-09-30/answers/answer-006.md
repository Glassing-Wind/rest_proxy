Question: Trace the major ranking and fallback stages used by code search.

The main `search_codebase` tool follows **hybrid retrieval → intent-aware ranking → targeted rescue → deduplication/diversity → top-k**, with an optional file-path grep supplement.

1. **Embedding and query interpretation.** The tool requires a query embedding before calling `search_codebase_core`; an empty embedding returns an error rather than switching to keyword-only search. The core identifies implementation intent, query class, exact identifiers, member expressions, and explicit/inferred path hints. [semantic.py:190](/Users/michaelmarler/Projects/rest_proxy/tools/brain/search/semantic.py:190), [code_retrieval.py:93](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:93)

2. **Initial hybrid ranking.** Each project supplies up to `min(k * 10, 150)` candidates. Semantic rank uses vector cosine distance; keyword rank uses PostgreSQL `ts_rank` with `websearch_to_tsquery`. Fusion is:
   `2 / (60 + semantic_rank) + 1 / (60 + keyword_rank)`.
   **Keyword-only hits cannot enter this initial pool:** the SQL left-joins keyword matches onto semantic candidates. Implementation queries also exclude certain grammar/parser-data paths at this stage. [code_retrieval.py:105](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:105), [code_retrieval.py:137](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:137)

3. **Empty-result rescue and scope filtering.** If retrieval returns nothing, implementation queries can recover indexed rows using runtime-entrypoint paths or path hints. If that fails, the function returns empty immediately. Otherwise it applies metadata/path/crate filters, including test exclusion by default. Broad mode raises the default directory cap from two to four, disables the default metadata boost, and enables grep fallback. [code_retrieval.py:196](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:196), [code_retrieval.py:242](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:242), [code_retrieval.py:328](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:328)

4. **Heuristic reranking and surface preference.** Ordinary queries receive metadata boosts and penalties for documentation, parser data, and binding surfaces. Implementation queries receive additional definition, identifier, path, entrypoint, and other intent-specific signals. The final ordering is **lexicographic**, with surface penalties and role/workflow priorities preceding identifier evidence and numeric score; RRF therefore does not determine final order. Implementation candidates are then reduced to ordinary code if available, otherwise parser data, binding surfaces, or documentation. [code_retrieval.py:353](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:353), [retrieval_surfaces.py:245](/Users/michaelmarler/Projects/rest_proxy/memory/retrieval_surfaces.py:245), [code_retrieval.py:394](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:394)

5. **Targeted rescue before final selection.** The first five candidates are inspected for missing path/entrypoint evidence. Additional indexed rows can be loaded and reranked. For definition-preferring queries, definition grep can discover paths whose indexed chunks are then loaded; this branch requires implementation intent, path hints, and existing results. Usage queries similarly use member-expression grep when the top candidates lack an exact usage-site hit. These rescues are independent of the public `fallback="grep"` option. [code_retrieval.py:427](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:427), [code_retrieval.py:487](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:487), [code_retrieval.py:522](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:522)

6. **Duplicate handling and diversity limits.** Optional graph-backed clone deduplication runs first. With file deduplication enabled, the postprocessor may invoke `ts_pack` duplicate/diversity selection, then reapplies implementation ordering and chooses one chunk per file. Dependency fallbacks try alternate runtime calls or duplicate analysis, ultimately retaining candidates when unavailable. Per-file and top-level-directory caps run before slicing to `k`. [code_retrieval.py:618](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:618), [code_retrieval_postprocess.py:39](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval_postprocess.py:39), [retrieval_duplicates.py:499](/Users/michaelmarler/Projects/rest_proxy/memory/retrieval_duplicates.py:499), [code_retrieval.py:640](/Users/michaelmarler/Projects/rest_proxy/memory/code_retrieval.py:640)

7. **Final grep supplement.** This runs only when grep fallback is enabled **and top results exist**, with either one unique file or a unique-file/result ratio at or below the threshold (default `0.4`). It returns separate file paths, without incorporating them into ranked results. The helper uses `rg -l` over an OR-pattern of query tokens; missing ripgrep, timeout, or execution failure produces no paths. It is therefore neither a general empty-search fallback nor whole-query exact matching. There is also a **separate lower-level search function** in `memory/store_search.py`: it uses equal-weight semantic/keyword RRF and falls back to Neo4j vector search when PostgreSQL is unavailable or raises an exception. The main tool explicitly calls `search_codebase_core`, so this database fallback should not be attributed to that tool’s pipeline.
